# 前端功能团队

四角色并行分析 + Team Lead 综合 + 单一写者实现 + 质量门禁。

## 触发条件

- fe-guild 工作流路由 B
- 用户主动 `/fe-feature-team`
- 中大型前端改动（多文件/跨模块/新页面/新接口）

## 设计理念

一个人写代码最大的风险：

1. **接口理解错** → 接口契约分析师
2. **规范跑偏** → 规范守护者
3. **方案欠考虑** → 实现设计师
4. **验证靠目测** → 测试设计师 + 门禁

四个角色**独立分析、独立给结论、互相挑战**。

Team Lead 综合价值在于找**矛盾**：四个都说"没问题"最可疑。

## 阶段零:澄清 + 评级 + 预检

### 第一步:需求澄清

**6维度确认**（与 triage 复用，不重问已确认项）:
- 业务目标 / 验收标准 / 接口契约 / UI形态 / 影响范围 / 时间约束

**发现模糊点** → AskUserQuestion 一次性汇总提问

### 第二步:上下文丰富度评级

| 等级 | 特征 | 策略 |
|------|------|------|
| A | PRD + 接口文档 + 设计稿 | 重点放在反面检验 |
| B | 有其一或其二的 | 结论标注置信度 |
| C | 只有口头描述 | 先出方案文档给用户确认 |

### 第三步:环境预检

1. 读项目画像，确认门禁命令
2. 确认依赖已安装 (`node_modules`)
3. 告知各Agent检索工具可用性

**预检不通过 → 先修复环境，不要带病开团**

### 四角色职责

| 角色 | 核心问题 | 输出 |
|------|----------|------|
| 接口契约分析师 | 数据从哪来？契约什么样？ | 接口清单/风险/mock方案 |
| 规范守护者 | 怎么写像这个项目的代码？ | 规范清单/参考映射/冲突 |
| 实现设计师 | 具体怎么改？有没有更好的方案？ | 方案对比/文件清单/分步计划 |
| 测试设计师 | 改坏了怎么第一时间知道？ | 测试用例/回归清单/边界场景 |

### Agent Prompt 模板

```
你是前端功能团队中的"{角色名}"，分析需求:{需求描述}

项目画像(项目特定事实以此为准，禁止自行另找口径):
{fe-profile.md 全文}

背景:上下文丰富度 {A/B/C} 级。{对应策略}

纪律:
- 你是只读角色:使用 Read/Grep{ /codegraph} 检索，禁止修改任何文件
- **读取失败禁止伪装**:检索不到的文件/接口必须如实报告"未能定位"
- 结论必须给出依据(文件路径 + 关键代码位置)
- 与其他角色可能矛盾的判断，大胆写出——矛盾是 Team Lead 综合的原料
```

## 阶段二:Team Lead 综合方案

**不是拼报告，是找交叉和矛盾**:

1. **共识点**: 多角色一致 → 置信度最高
2. **矛盾点**: 逐条裁决，说明取舍
3. **被忽略的角落**: 错误处理/权限/埋点

**产出**: 实现方案定稿（JSON格式）
```json
{
  "consensus": ["..."],
  "conflicts": [{"issue": "", "resolution": ""}],
  "neglected": ["..."],
  "finalPlan": {
    "files": [{"file": "", "action": "", "reason": ""}],
    "steps": [{"step": 1, "description": "", "verify": ""}]
  }
}
```

**方案级分歧无法裁决时 → 停下来问用户**

## 阶段三:实现

**Team Lead 亲自完成，不委托 Agent**

- 严格按阶段二定稿实施
- 实施中发现问题 → 回到阶段二修订，不悄悄改方案
- 写法对齐规范守护者给出的参考实现
- 公共区域修改同步检查测试设计师列出的调用方

## 阶段四:质量门禁 + 维护者评审

### 质量门禁（Team Lead 前台执行）

**按画像门禁命令执行**:

```bash
{lint检查}      # 必跑
{format检查}    # 画像配置了则必跑
{测试命令}      # 必跑；无测试则记录缺口
{构建命令}      # 涉及依赖/路由时必跑
```

**铁律**: 工具说了算，LLM 不目测

### 代码评审 Agent（后台，只读）

**视角**: "一年后接手这段代码的维护者"

| 维度 | 权重 | 检查 |
|------|------|------|
| 正确性 | 40% | 逻辑/边界/异常流/接口契约 |
| 规范 | 25% | 风格/与参考实现偏差 |
| 回归风险 | 20% | 公共区域/隐式依赖 |
| 可维护性 | 15% | 命名/结构/可读性 |

### 准出/打回

- **【准出】** 门禁全绿 + 评审硬伤清零
- **【打回】** 修复后重跑门禁再准出

## 纪律红线

1. **并行启动必须在 Workflow 中** —— 使用 `parallel()` 确保真正并行
2. **分析 Agent 全部只读** —— 后台Agent无法弹权限确认
3. **工具失败禁止伪装** —— 读不到的代码/跑不了的命令如实标注
4. **确定性验证下放给工具** —— 代码质量/格式/测试门禁说了算
5. **单一写者** —— 实现只由 Team Lead 做
6. **综合找矛盾** —— 都说"没问题"时必须主动挑战
7. **澄清不留到实现后** —— 阶段零没澄清的实现后发现最贵
8. **项目特定事实只从画像来** —— skill 中不内嵌具体路径/命令
