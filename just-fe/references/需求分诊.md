# 需求分诊 · 路由判断与范式接入

① 需求梳理由 `stages/01-triage.md` 阶段卡执行。**分析动作以《需求处理范式》为准**，本文只管两件事：范式从哪来、`route` / `stackScope` 怎么用。

## 一、需求处理范式从哪来

范式是用户自己的通用方法论（阶段一 需求榨取：IN / MD / IM / DC；阶段二 协作降维：DV），不绑技术栈，**留在用户目录、不复制进本 Skill**。

- `tools/workspace-detect.js` 会在会话区下找 `需求处理范式.md`，输出到 `paradigm` 字段
- 编排方把范式全文作为 `paradigm` 入参传给 ① 的子 agent；人设收到后按范式阶段一全部动作与质检门执行
- 没传范式时，人设按内置最小集执行，其中 `MD-3` 覆盖缺口反推、`IM-2` 存量消费方排查、决策卡六项齐全三条不可裁剪

范式阶段二（DV-1…12）的结构被契约文档借用——契约的读者正是「只关心自己那块的协作方」。见 `stages/02-contract.md` 的「协作结构」。

## 二、route：三档深度

| route | 判定 | 流程裁剪 |
|-------|------|----------|
| `light` | 单文件 / 可复现 bug / 接口就绪无需契约 / 无公共组件影响，影响面 ≤ 3 文件 | 跳过 ②③（契约与方案评审）；④ → ⑥（单评审员即可）→ ⑦（只跑门禁，不打分）→ ⑧ |
| `full` | 多文件 / 跨模块 / 新页面 / 新接口 / 接口变更 | 全流程 |
| `blocked` | 接口未定、设计稿未定、验收标准不清 | 停在 ①，决策卡交用户 |

`route` 由 ① 产出，编排方在闸门处向用户汇报并确认；用户可以覆盖（例如小需求也想走 full）。**`light` 不是跳过 Review**：只是把 ③ 和 ⑦ 的打分压缩，⑥ 仍要过。

## 三、stackScope 与接口三态

| stackScope | 含义 | 启动的泳道 |
|------------|------|-----------|
| `fe` | 只改前端；接口全部 `existing` | fe；契约阶段退化为「勘察 + 复用清单」 |
| `be` | 只改后端 | be；无 UI 阶段 |
| `fullstack` | 两边都改；至少一个接口 `new` / `change` | fe + be + 契约 + 部署闸门 |

接口三态是 ① 的硬产出：

- `existing`：必须附证据位置（后端 `类#方法` + 前端调用点），写不出证据不许标 existing
- `new`：谁消费、谁提供、落在后端哪个模块
- `change`：必须关联存量消费方排查结论

任一 `new` / `change` 都要求 `repos[be].mode = write`。① 返回 `needsBackendWrite=true` 而 MEMORY 里后端仓是 `readonly` 时，编排方停下问用户：改为可写，还是契约只定义不实现、交后端团队。

## 四、六关（用于路由判定的快速自检）

| 关 | 问题 | 不过时 |
|----|------|--------|
| 能力圈 | 我理解这个业务域吗 | 停下问用户 |
| 影响面 | 会碰到哪些文件（两仓都查） | 查不到标「未能定位」，禁止编造 |
| 接口依赖 | 数据从哪来、三态是什么 | 有 new / change → 契约阶段必走 |
| 规范冲突 | 和两仓的 CLAUDE.md / 画像有没有矛盾 | 标注需用户确认 |
| 回归风险 | 会破坏什么（IM-2 的结论） | 列进影响面与回归点 |
| 测试可行 | 怎么验证（前端 E2E 打联调环境；后端单测 + 契约测试） | 列必跑门禁命令 |

## 五、镜子测试（① 结束前）

五句话复述需求：改什么 / 影响哪些页面与文件（两仓）/ 依赖哪些接口、三态如何 / 最大回归风险 / 怎么验证。说不完整 → 回到台账与术语表。

## 六、纪律红线

1. 本阶段不写业务代码——只做分析与路由
2. 模糊需求不进实现——决策卡没拍板的点，下游不许替用户决定
3. 现状从代码里查——查不到标「未确认」，禁止编造
4. 项目特定事实只从画像与 CLAUDE.md 读取——画像缺失先走 `references/项目画像初始化.md`
