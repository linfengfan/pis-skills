# just-fe · 全栈研发流程 Skill

给 Claude Code / Cursor 装上一条研发流水线：**需求梳理 → 接口契约 → 方案（前端 / 后端）→ 方案评审 → 开发（前端 UI / 后端接口）→ 部署闸门 → 契约校验与联调 → 代码 Review → 测试评估 → 变更说明与提交清单**。四道关卡打分、80 分红线、不到分打回；每个阶段结束停下来问你；所有产物落在会话区；中途断了能接着跑；**提交永远由你自己做**。

它解决的是「让 AI 直接写代码」的老问题：需求没问清就开工、前后端各猜各的接口、写完没人认真审、审了也不知道审到什么程度、AI 顺手把东西 commit 了。

- **适合**：新页面、新接口、跨前后端的功能，需要契约先行、方案先行、代码要过评审的需求
- **不适合**：改一行文案、修一个单文件明显 bug——直接让 AI 改就行
- **与 just-flf 二选一**：两者触发条件相近，同时安装时模型不知道该用哪个。just-fe 面向「后端经部署闸门发布到 dev 再联调」的团队工作区

| 你想做什么 | 怎么做 |
|-----------|--------|
| 安装 | 对 AI 说「读 `just-fe/INSTALL.md`，帮我装上」 |
| 使用 | 读本文 |
| 卸载 | 对 AI 说「读 `just-fe/UNINSTALL.md`，彻底删掉」 |
| 改流程 / 人设 / 评分维度 | 直接改 `stages/*.md`（阶段卡即唯一真源），见文件一览 |

---

## 1. 它假设你的工作区长这样

```
~/dev/
├── xxx.code-workspace          ← folders: sessions / <前端仓> / <后端仓>
├── sessions/                   ← 会话区
│   ├── 新需求/<需求短名>/        ← 流程产物都在这里（report_dir）
│   └── …/需求处理范式.md         ← 你的需求分析方法论，① 会引用
├── <前端仓>/                    ← git；.claude/fe-profile.md
└── <后端仓>/                    ← git；.claude/be-profile.md；.workflow/*.yml 是部署流水线
```

三个目录并列、两个仓各自独立 git、后端不能本地跑完整应用（依赖 dev 环境）。只有前端仓也能用——后端泳道不启动。

## 2. 30 秒上手

在工作区里对 AI 说：

```
用 just-fe 走一遍：<粘贴需求文档 / 原型链接>
```

接下来会发生的事：

1. **⓪ 工作区确认**：它跑 `tools/workspace-detect.js` 探测三个目录、分支、画像、dev 网关地址，问你三件事——后端仓本次**可写还是只读参考**、本期做到哪个阶段、需求来源优先级。写进 `sessions/新需求/<需求>/MEMORY.md`。缺画像会先生成（也要你确认）
2. **① 需求梳理**：按你的《需求处理范式》出台账、术语表、场景矩阵与覆盖缺口、存量消费方排查、决策卡；判定技术栈范围（前端 / 后端 / 全栈）和每个接口是**已有 / 新增 / 变更**。停下来让你逐张拍决策卡
3. **② 契约**（有接口才跑）：先勘察后端仓已有接口，再按后端 `CLAUDE.md` 的接口约定定义字段、可空、错误码、幂等；3 个评审员打分，<80 打回升版本。定稿后它是前后端唯一的接口真源
4. **②③ 方案与评审**：前端、后端各出一份方案、各过 6 维评审，<80 打回，最多 3 轮
5. **④ 开发**：前端按契约生成 Mock 做 UI；后端实现接口并**必须为每个契约接口写契约测试**，本地编译 / 格式 / 测试过。两边只改需求涉及文件
6. **🚀 部署闸门**：它先给你后端的待提交清单和建议 commit message（开发 agent 不提交，合入前要你先在特性分支提交），再给「合入 dev 并 push」的命令、会触发的流水线、需要先在 dev 库执行的 DDL 和需要配置的网关路由；**你执行**，回复「已部署」和网关地址
7. **⑤ 联调**：它用脚本对 dev 网关逐接口校验契约（字段、类型、可空、统一响应体 code；错误码分支由后端契约测试覆盖），默认只发只读请求，写接口要你同意才发；PASS 的接口替换 Mock，FAIL 的不做前端补丁、打回后端
8. **⑥⑦ Review 与测试**：每个仓各一次 7 维代码 Review（越界改动由脚本算）、各一次测试评估（前端 E2E 打 dev 网关，后端单测 + 契约测试）。<80 或一票否决打回，最多 2 轮
9. **⑧ 变更说明 + 提交清单**：每个仓一份「建议 add 的文件、建议先回退的越界文件、建议 commit message、合入命令」。**流程到此结束，commit 由你决定**

第一次用建议拿一个小需求试跑，感受闸门节奏和分数口径。

## 3. 日常用法

### 闸门三选一

每个阶段结束你都会看到同一个问题：**进入下一阶段** / **本阶段还有调整** / **先停在这里**。它不会因为「上一阶段 95 分」替你决定往下走。

### 不想逐阶段确认：`--auto`

`/just-fe --auto <需求>` 连续跑，但这些仍会停：需求阻断、决策卡、缺设计稿、后端仓只读却要改接口、评审打回、达轮次上限、部署闸门、契约校验 FAIL。

### 从中间开始 / 点名阶段

```
/just-fe --from=⑥ --lane=be       # 后端代码 Review
/just-fe --from=⑤                 # 跑契约校验 + 联调
/just-fe --resume                 # 读 MEMORY 找断点
```

自然语言也行：「出契约」「后端开始写接口」「部署好了」「审一下前端代码」。它先改 MEMORY 的当前阶段，问你中间阶段算完成还是跳过，再开跑。

### 只做到某个阶段

⓪ 时说「本期只做到方案」，MEMORY 记 `scope: ②`，流程到 ③ 闸门停。

### 后端只读参考

⓪ 时说「后端仓只读」：前端消费已有接口，契约阶段只出复用清单与证据，后端泳道不启动。① 发现有接口要新增 / 变更时它会停下来问你改不改成可写。

## 4. 开始之前准备什么

| 东西 | 位置 | 缺了会怎样 |
|------|------|-----------|
| 前端画像 | `<前端仓>/.claude/fe-profile.md` | 方案与评审按通用实践打分；⑦ 不知道用什么命令；首次自动生成 |
| 后端画像 | `<后端仓>/.claude/be-profile.md` | 同上；且缺「模块 → 流水线 → dev 域名」表，部署闸门给不出流水线清单；首次自动生成 |
| 需求处理范式 | 会话区任意子目录 `需求处理范式.md` | ① 退化为内置最小集（仍保留覆盖缺口反推、存量消费方排查、决策卡） |
| 需求文档里的验收标准、设计稿 / 原型链接 | — | 没有也能跑，会多被问几次 |
| dev 环境鉴权 | 本地文件，如 `~/.just-fe/auth`，每行一个 `Header: value`，`chmod 600` | 契约校验全部 UNVERIFIED，⑤ 只写接入代码不宣称验证 |

鉴权凭证写在本地文件里，不要贴进对话；MEMORY 只记文件位置。

## 5. 分数怎么看

| 关卡 | 维度 | 通过 | 不过 |
|------|------|------|------|
| ③a 契约评审 | 字段对齐 40 / 错误流 30 / 后端约定合规 30 | ≥ 80 | 升版本重出，最多 2 轮 |
| ③ 前端方案 | 需求覆盖 25 / 可行性 20 / 模块结构 20 / 状态管理 15 / 风险 10 / 规范 10 | ≥ 80 | 打回方案，最多 3 轮 |
| ③ 后端方案 | 需求覆盖 20 / 分层与契约落地 20 / 数据模型与索引 20 / 事务·并发·幂等 20 / 性能与安全 10 / 规范 10 | ≥ 80 | 同上 |
| ⑥ 代码 Review（每仓） | 逻辑 25 / 健壮性 20 / 架构 15 / 类型 10 / 规范 10 / 安全 10 / 爆炸半径 10，每维按前端 / 后端套清单 | ≥ 80 **且无 🔴** | 打回开发，最多 2 轮 |
| ⑦ 测试评估（每仓） | 需求覆盖 30 / 边界异常 20 / 回归 20 / 异常处理 15 / 测试质量 15 | ≥ 80 **且无否决项** | 打回开发（源于方案则回方案），最多 2 轮 |

一票否决：⑥ 任一 🔴；⑦ 任一验收取证失败 / 回归失败 / 契约测试失败；⑤ 契约校验任一 FAIL 不进 ⑥。`unverified` 的条目进「人工 / 联调环境验证清单」，提交前你自己过。

上表是速览，维度与配分以各阶段卡为准；汇总公式与轮次见 `references/评分口径.md`。

## 6. 常见场景

| 你遇到的 | 它会怎么做 | 你该怎么做 |
|----------|-----------|-----------|
| 需求里有新接口，但后端仓是只读 | 🔐 停下问 | 改可写由流程实现，或保持只读、把契约交给后端团队 |
| 后端写完了要联调 | 🚀 先给待提交清单，再给合入 dev 的命令、流水线、DDL 与网关路由 | 你先提交、再合入部署，回复「已部署」+ 网关地址 |
| 部署后后端又改了代码 | 重新走 🚀（提交、合入、部署）再跑 ⑤ | 照做 |
| 契约校验有 FAIL | ⑤ 不进 ⑥，FAIL 接口保留 Mock | 后端修实现，或契约升版本重评，重新部署后再跑 ⑤ |
| 后端需要 DB 的集成测试跑不了 | ⑦ 标 unverified 进人工清单 | 在 dev 环境或 CI 上验 |
| 需求里没有设计稿 | ④-FE 前停下要 | 给链接（Figma / 在线原型 / 截图），或明确说「没有设计稿，按现有风格实现」 |
| 评审打回到上限还不过 | 停下交给你 | 放宽、人工改、或拆需求 |
| 上下文丢了 | — | `/just-fe --resume` |
| 担心 AI 顺手格式化 / 顺手 commit | 开发 agent 只改需求涉及文件、不碰 git；⑥ 用脚本算越界；⑧ 只给清单 | 看 ⑧ 的「建议先回退」和清单，自己 commit |

## 7. 注意事项

- **只有一种执行方式。** 编排者（主 agent）读阶段卡派子 agent 执行，Claude Code 与 Cursor 通用，没有模式切换。子 agent 参数形态见 `references/运行时排错.md`。
- **打分是模型判断，不是确定性检查。** 能用工具证明的事（lint / 类型 / 单测 / 契约校验 / 越界改动）都交给工具跑；打分只覆盖工具管不到的层面。
- **后端不能本地跑是设计前提。** 本地只跑编译、格式、单测与切片级契约测试；真实接口验证发生在 dev 环境。
- **尚未端到端跑过完整 fullstack 流程。** 三个 `tools/` 对真实工作区试过；遇到问题记到 `todo.md`。

## 8. 文件一览

```
just-fe/
├── README.md / INSTALL.md / UNINSTALL.md
├── SKILL.md              # 入口：编排协议、闸门、评分铁律（模型读）
├── MEMORY.md             # 流程状态模板，⓪ 时复制到 <report_dir>/
├── stages/               # 9 张阶段卡（唯一真源：人设、schema、公式、报告模板都在卡里）
├── roles/                # fe-dev.md：④-FE 与 ⑤ 共用的人设（唯一跨卡共享，防漂移）
├── tools/                # 确定性工具：workspace-detect.js / contract-conformance.js / out-of-scope.sh
├── templates/            # 画像（fe / be）、变更说明与提交清单
├── references/           # 评分口径、项目画像初始化、需求分诊（route / 范式接入）、运行时排错
├── docs/                 # 设计文档与研讨纪要
└── todo.md               # 使用反馈与处理记录
```
