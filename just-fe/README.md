# just-fe · 前端研发全流程 Skill

给 Claude Code 装上一条前端研发流水线：**需求梳理 → 方案架构 → 方案评审 → UI 开发 → 接口联调 → 代码 Review → 测试评估 → 提交**。三道关卡打分、80 分红线、不到分打回重做；每个阶段结束停下来问你，你点头才往下走；所有产物落盘，中途断了能接着跑。

它解决的是「让 AI 直接写代码」的三个老问题：需求没问清就开工、写完没人认真审、审了也不知道审到什么程度。

- **适合**：新页面、新功能、跨多个文件的改造，需要方案先行、代码要过评审的需求
- **不适合**：改一行文案、修一个明显的 bug——直接让 Claude 改就行，没必要走七道关

三份文档的分工：

| 你想做什么 | 怎么做 |
|-----------|--------|
| 安装 | 对 Claude 说「读 `just-fe/INSTALL.md`，帮我装上」——[INSTALL.md](./INSTALL.md) 是给 AI 的完整安装指令 |
| 使用 | 读本文 |
| 卸载 | 对 Claude 说「读 `just-fe/UNINSTALL.md`，彻底删掉」——[UNINSTALL.md](./UNINSTALL.md) 是给 AI 的卸载指令 |

## 1. 30 秒上手

装好之后，在你的前端项目里对 Claude 说一句话：

```
用 just-fe 走一遍：<粘贴需求文档>
```

或者更随意一点：

```
帮我按前端研发流程做「商品详情页收藏按钮」，设计稿 https://figma.com/file/xxx
```

接下来会发生的事：

1. 它先看项目里有没有 `.claude/fe-profile.md`（项目画像）。没有就先探测你的技术栈、门禁命令、目录约定，让你确认后写盘
2. 从 ① 需求梳理开始跑。**每个阶段结束都会停下来**：告诉你产物写在哪、得了多少分、还有哪些待决问题，然后问你三选一——进入下一阶段 / 本阶段还要调整 / 先停在这里
3. 你选「进入下一阶段」它才继续；评审不过线会自动打回上一阶段重做
4. 全部跑完，它写一份变更说明，只把本次需求涉及的文件 `git add`，然后 commit

第一次用建议拿一个小改动试跑，感受一下闸门的节奏和分数的口径，再上真需求。

## 2. 八个阶段，你会看到什么

| 阶段 | 它做什么 | 你会被问什么 | 落盘产物 |
|------|----------|--------------|----------|
| ① 需求梳理 | 读项目现状，把需求里模糊、矛盾、隐含假设的点列出来，给出验收标准和影响面 | 必须由人回答的「待决问题」；需求有死锁会直接阻断 | `triage-{日期}.md` |
| ② 方案架构 | 出技术方案：文件清单、组件树、状态归属、接口契约、任务卡 | 需求信息不足时列出要补什么 | `architecture-{日期}.md` |
| ③ 方案评审 | 6 个维度并行打分 | <80 分自动打回②，最多 3 轮；过线后问你是否进 ④ | `arch-review-{日期}.md` |
| 🎨 设计稿闸门 | 检查需求是否涉及界面改动、有没有设计稿 | 涉及界面但没设计稿：要你给链接，或明确说「没有设计稿，按现有风格实现」 | 记入 `MEMORY.md` |
| ④ UI 开发 | 用 Mock 数据把界面做出来，只改需求涉及的文件 | 逻辑死锁时停下 | `ui-{日期}.md` |
| ⑤ 接口联调 | 先出前端依赖接口清单，再接真实接口、去掉 Mock | 有接口没就绪会停下等你 | `api-list-{日期}.md`、`integration-{日期}.md` |
| ⑥ 代码 Review | 7 个维度并行审，扣分指到 `文件:行号`，顺带检查有没有越界格式化 | <80 分或有 🔴 致命问题打回④⑤，最多 2 轮 | `code-arch-review-{日期}.md` |
| ⑦ 测试评估 | 先按验收标准跑 E2E / 回归取证，再以证据打分 | 任一验收失败或回归失败直接打回；没法自动验证的条目让你人工确认 | `test-assessment-{日期}.md` |
| ⑧ 完成 | 写变更说明，只 add 需求涉及文件，commit | 最后一次确认 | `change-{日期}.md` |

所有产物在项目根的 `fe-reports/{需求名}/` 下，外加一份 `MEMORY.md` 记录当前阶段、每一轮分数、你在每个闸门的决定。建议把 `fe-reports/` 加进 `.gitignore`，除非团队想留评审档。

## 3. 日常用法

### 3.1 闸门：三个选项怎么选

每个阶段结束你都会看到同一个问题，三个选项：

| 选项 | 什么时候选 | 之后发生什么 |
|------|-----------|-------------|
| **进入下一阶段** | 产物你看过了，没意见 | 它读磁盘上的产物拼好入参，调下一阶段 |
| **本阶段还有调整，继续做** | 报告里有你不同意的地方、想补的点 | 你说修改点，它在**当前阶段内**改、重新落盘、再问你一次 |
| **先停在这里** | 要去开会、要等后端、今天不想继续 | 它把中断原因记进 `MEMORY.md`，下次 `--resume` 接着来 |

闸门是默认行为，目的就是让你掌握节奏。它不会因为「上一阶段 95 分」就替你决定往下走。

### 3.2 不想逐阶段确认：`--auto`

```
/just-fe --auto <粘贴需求文档>
```

`--auto` 会连续跑，但这几种情况**仍然会停下来问你**：需求死锁、缺设计稿、接口未就绪、评审打回、达到轮次上限。也就是说它只跳过「一切正常时的点头」，不跳过需要你拍板的事。

### 3.3 从中间开始 / 直接点名阶段

产物都在磁盘上，所以可以只跑后半段：

```
/just-fe --from=⑥                      # 从代码 Review 开始，自动读 ①~⑤ 的产物
/just-fe --from=⑤ --需求="商品详情页"    # 从接口联调开始
```

用自然语言点名也行，「开始代码评审吧」「帮我出个方案」「跑一下测试评估」都能识别。它会先把 `MEMORY.md` 的当前阶段改成你点名的阶段，问你一句中间跳过的阶段算「确认完成」还是「跳过」，再开跑。之后它汇报的阶段名以 `MEMORY.md` 为准，不会你已经要求评审、它还说自己在做 UI。

### 3.4 中断后恢复

```
/just-fe --resume
```

它读 `fe-reports/{需求}/MEMORY.md` 找到断点，检查前置产物是否完整，从断点继续；不重跑已经通过的阶段，不重问已经澄清过的问题。上下文被压缩、会话重开、换了台机器（只要 `fe-reports/` 在），都靠这条命令。

### 3.5 只跑某一个阶段

装了 Workflow 脚本（INSTALL.md 模式 B/C）的话，7 个阶段各自是一条命令，可以单独用：

| 命令 | 用途 |
|------|------|
| `/fe-triage` | 只想把需求问清楚，先不动手 |
| `/fe-architecture` | 只要一份技术方案和任务卡 |
| `/fe-architecture-review` | 给一份现成的方案打分 |
| `/fe-ui-implementation` | 只做界面 |
| `/fe-api-integration` | 只做接口清单和联调 |
| `/fe-code-arch-review` | 给当前分支的改动做一次 7 维 Review |
| `/fe-test-assessment` | 给当前改动跑 E2E 取证并评估 |

单跑时把上下文说清楚，比如：

```
/fe-code-arch-review 审当前分支相对 main 的改动，需求是「商品详情页收藏按钮」
```

不要什么都不带就敲命令——脚本拿不到需求描述，评审只能从 diff 猜你想干什么，结论会标注置信度降低。

## 4. 开始之前准备什么

**项目画像 `.claude/fe-profile.md`。** 它记录你项目的技术栈、lint / test / e2e / dev server 命令、接口层位置、路由注册方式、高风险文件、参考实现。没有它，方案和评审只能按「通用前端最佳实践」打分，规范一致性这一维会失真；⑦ 阶段也不知道用什么命令跑 E2E。第一次跑流程时它会自动帮你生成，生成后可以手改，重跑不会覆盖你手改的内容。

**需求文档里最好有三样东西：**

| 缺了会怎样 | |
|------|------|
| 验收标准 | ① 会产出大量「待决问题」，⑦ 没有可取证的条目 |
| 接口契约 / 文档 | ⑤ 大概率停在「等接口就绪」 |
| 设计稿链接 | ④ 之前会被设计稿闸门拦住要链接 |

没有也能跑，只是会多被问几次。

## 5. 分数怎么看

三道关卡的口径：

| 关卡 | 满分构成 | 通过条件 | 不过怎么办 |
|------|----------|----------|-----------|
| ③ 方案评审 | 需求覆盖 25 / 技术可行性 20 / 模块结构 20 / 状态管理 15 / 风险识别 10 / 规范一致性 10 | ≥ 80 | 打回②重写方案，最多 3 轮 |
| ⑥ 代码 Review | 逻辑正确性 25 / 健壮性 20 / 架构 15 / 类型安全 10 / 规范 10 / 安全与可访问性 10 / 爆炸半径 10 | ≥ 80 **且没有 🔴 致命问题** | 打回开发，最多 2 轮 |
| ⑦ 测试评估 | 需求覆盖 30 / 边界异常 20 / 回归覆盖 20 / 异常处理 15 / 代码质量 15 | ≥ 80 **且没有验收失败 / 回归失败** | 打回架构 + 开发，最多 2 轮 |

两条一票否决，和总分无关：

- ⑥ 出现任何 🔴 致命问题（密钥硬编码、未转义注入、越权入口、未清理的定时器 / 监听导致内存泄漏），97 分也不过
- ⑦ 任一验收标准的 E2E 跑失败，或既有测试出现回归，直接打回

读报告时看这几处就够：

- **分项评分表**：哪一维掉分
- **问题清单**：🔴 必须修 / 🟡 应该修或记录取舍 / 🟢 可选；每条带 `文件:行号` 和修法。评审员找不到真问题时会如实给高分，不会为了显得严格编扣分项
- **⑦ 的验收标准逐条结果**：✅ 跑过、❌ 跑挂、⏳ 没法自动验证——⏳ 的条目会汇总到「必须人工验证的点」，合并前你要自己过一遍
- **待确认**：评审员拿不准的地方，不伪装成结论

打回之后你不用做什么，它会把问题清单原文带回上一阶段重做；达到轮次上限才会停下来交给你。

## 6. 常见场景

| 你遇到的 | 它会怎么做 | 你该怎么做 |
|----------|-----------|-----------|
| 需求里没有设计稿 | ④ 之前停下来要 | 给链接（Figma / 蓝湖 / MasterGo / 截图都行），或明确说「没有设计稿，按现有风格实现」。含糊的「你看着办」不算 |
| 后端接口还没好 | ⑤ 出完接口清单后停在「等接口就绪」 | 拿着清单去对接口；就绪后 `/just-fe --from=⑤` |
| 评审打回了 | 自动带着问题清单回上一阶段重做 | 等结果；想插手就在闸门处选「本阶段继续」 |
| 打回到轮次上限还不过 | 停下来交给你 | 看报告决定：放宽、人工改、或者拆需求 |
| 需求不涉及界面 | 设计稿闸门问你要不要跳过 ④ | 确认跳过，直接进 ⑤ |
| 想跳过某个阶段 | 点名下一阶段即可 | 「直接开始联调」——它会问前面的阶段怎么记 |
| 上下文丢了 / 会话重开 | — | `/just-fe --resume` |
| 觉得每步都问太啰嗦 | — | 用 `--auto`；需要你拍板的地方仍会停 |
| 担心 AI 顺手格式化全局代码 | 开发 agent 被要求只改需求涉及的文件，收工前用 `git diff --stat` 自查回退无关改动；⑥ 再复核一次，越界改动会被记问题 | 看 ⑥ 报告的「越界改动」条目 |
| 报错 `Unknown skill: 前端开发工程师` | 旧版本问题。脚本里的角色名被当成了外部 Skill | 更新到当前版本 |
| 报错 `undefined is not an object (evaluating 'context.requirement')` | 旧版本问题。不带参数调 workflow 导致 | 更新到当前版本；单跑命令时把需求说清楚 |

## 7. 注意事项

- **只装了 Skill、没装 Workflow 脚本时**（INSTALL.md 模式 A），打分不是真并行：评审退化成主对话里的一次判断，隔离性靠模型自觉。要真跑并行打分请装模式 B 或 C。
- **打分是模型判断，不是确定性检查。** lint、类型检查、单测、E2E 这些能被工具证明的事，⑦ 阶段会交给工具跑；评分覆盖的是工具管不到的架构与需求层面。它能压住最坏情况，不能替代 CI。
- **Cursor 用户**：Skill 结构兼容，放到 `~/.cursor/skills/just-fe/` 即可；但 Cursor 没有 Dynamic Workflow 运行时，等价于模式 A。
- **未做过真实运行时的端到端验证。** 脚本逻辑用桩运行时测过，编排协议用子 agent 场景推演过，但没在真实 Claude Code 里完整跑过七个阶段。遇到问题欢迎记到 `todo.md`。

## 8. 文件一览

```
just-fe/
├── README.md        # 本文：怎么用
├── INSTALL.md       # 给 AI 的安装指令 + 环境要求 + 设计约束
├── UNINSTALL.md     # 给 AI 的卸载指令
├── SKILL.md         # 入口：编排协议、闸门、评分铁律（模型读，用户一般不用看）
├── MEMORY.md        # 流程状态模板，运行时复制到 fe-reports/{需求}/
├── todo.md          # 使用反馈与处理记录
├── scripts/         # 7 个阶段的 Dynamic Workflow 脚本
├── templates/       # 项目画像 / 需求报告 / 方案 / 评分协议 / 变更日志 的格式
└── references/      # 项目画像初始化、需求分诊六关、四角色并行分析
```
