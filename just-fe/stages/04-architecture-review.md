# 阶段 ③ · 方案评审（dev-architecture-review，lane=fe | be）

> 6 个评审员**同一条消息并行**派出，按派出顺序（下标）对应维度，不信 agent 回填的 dimension 字段。每维 `score = min(返回值, maxScore)`；6 个维度必须全部返回，缺失的维度原样重派一次，仍缺失 → 本轮判「无法完成」，停下交用户，不计分。子 agent 调用约定见 `references/运行时排错.md`。

## 入参

| 入参 | 必填 | 来源 | 说明 |
|------|------|------|------|
| `architecture` | ✅ | 最新的 `{lane}/architecture-{日期}-r{轮次}.md` 全文 | 空 → `invalid_args` |
| `lane` | ✅ | 泳道 | 决定维度组 |
| `round` | 默认 1 | 轮次 | 最多 3 轮 |
| `contract` | 推荐 | `contract-v{N}.md` 全文 | 方案引用的契约 id 必须存在于此 |
| `requirementAnalysis` | 推荐 | ① 的 analysis | 验收标准 / 决策卡 / 消费方排查 |
| `profile` | 强烈推荐 | 对应画像全文 | 规范唯一基准 |

## 评审员纪律（每个维度 prompt 开头都带）

你是架构方案评审员，只负责**一个指定维度**。只审查不改写方案；只报你负责的维度；每条 issue 指到方案里的具体章节 / 文件 / 契约 id；找不到真实问题时如实给高分并说明「本维度未发现问题」，严禁为了压分编造问题；无法判定的写进 pendingConfirmations。项目画像与契约文档是唯一评判基准。输出用中文。

## 每个维度的 prompt 组成

评审员纪律 + 「你评审「{label}」维度（{maxScore}分）」+ 该维度正文 + `## 方案文档（评审对象）` + `## 契约文档` + `## 需求梳理结果` + `## 项目画像` + `## 本维度满分 N 分` + 「输出 JSON：dimension 固定填 "{key}"，maxScore 固定填 {maxScore}」+ `DIMENSION_SCHEMA` 尾注

## DIMENSION_SCHEMA

```json
{
  "type": "object",
  "properties": {
    "dimension": { "type": "string" },
    "score": { "type": "number" },
    "maxScore": { "type": "number" },
    "findings": { "type": "array", "items": { "type": "string" } },
    "issues": { "type": "array", "items": { "type": "object", "properties": { "location": { "type": "string" }, "issue": { "type": "string" }, "fix": { "type": "string" } }, "required": ["issue"] } },
    "pendingConfirmations": { "type": "array", "items": { "type": "string" } },
    "recommendation": { "type": "string" }
  },
  "required": ["dimension", "score", "maxScore"]
}
```

## lane=fe 六个维度（合计 100）

### `requirement-coverage` 需求覆盖（25）
- 25分: 完整覆盖所有需求点与验收标准，每条用户故事都有对应设计
- 20分: 覆盖主要需求，有小遗漏
- 15分: 覆盖部分核心需求
- 10分: 遗漏重要需求
- <10分: 严重遗漏

必须逐项检查：
1. 需求梳理的范围边界（做什么 / 不做什么）是否被方案尊重，有没有越界设计
2. 每条验收标准能否在方案里找到落点（哪个组件 / 哪条数据流负责它）
3. 需求梳理列出的异常流与边界（空 / 失败 / 极值 / 竞态）是否都有处理设计
4. 需求梳理的决策卡若已被用户拍板，方案是否按拍板结果设计；未拍板的是否被方案擅自决定

### `technical-feasibility` 技术可行性（20）
- 20分: 完全基于项目既有技术栈与依赖，方案可直接实现
- 15分: 方案可行，有一定实现难度或需少量新依赖且理由充分
- 10分: 存在未验证的技术点，需要先做验证
- <10分: 引入项目未采用的范式或技术风险过高

必须逐项检查：
1. 方案用到的框架特性、库、API 在项目当前版本里是否存在
2. 新增依赖是否必要，是否说明了为何现有依赖不能实现
3. 是否有「看起来能做、实际上框架不支持」的设计
4. 契约引用是否真实：方案引用的契约 `id` 是否都存在于契约文档

### `module-structure` 模块结构（20）
- 20分: 模块划分清晰，职责单一，完全解耦，文件清单可直接照做
- 16分: 模块划分合理，个别边界模糊
- 12分: 存在职责混杂或重复实现
- <12分: 模块划分混乱

必须逐项检查：
1. 文件清单是否完整（新增 / 修改 / 删除都列了），路径是否符合项目目录约定
2. 组件树的 Smart / Dumb 划分是否清晰，Props/Emits 契约是否写出类型签名
3. 是否复用了项目既有组件 / composable / 工具，新建的是否说明了不能复用的理由
4. 是否有循环依赖风险、跨模块越界引用
5. 单文件体量是否会超项目阈值而方案未安排拆分

### `state-management` 状态管理（15）
- 15分: 状态归属清晰且有理由，数据流与竞态处理完整
- 12分: 状态管理基本合理，个别归属理由不足
- 8分: 局部状态被放进全局 store，或竞态未处理
- <8分: 状态管理混乱

必须逐项检查：
1. 组件本地状态 vs 全局 store vs URL query 的划分是否恰当，「为什么不放全局」是否写了
2. 请求时机、缓存与失效策略是否明确
3. 并发与竞态（切换条件时旧响应覆盖新响应、重复提交）是否有处理方案
4. 契约里可空字段到视图模型的规整层是否明确在哪一层做
5. Mock 方案是否能在联调时整体移除而不留残余

### `risk-identification` 风险识别（10）
- 10分: 风险识别完整，缓解措施具体可行，爆炸半径写清了回归点
- 8分: 识别主要风险，有缓解方案
- 5分: 部分风险识别，缓解措施空泛
- <5分: 风险识别不足

必须逐项检查：
1. 是否识别了技术风险（性能、兼容、构建体积、内存泄漏点）
2. 是否识别了业务风险（口径误读、权限、国际化遗漏）
3. 爆炸半径：改动的公共组件 / store / 请求层会波及哪些页面，回归点是否列出
4. 缓解措施是否可执行，而不是「注意」「加强」之类的空话
5. 方案取舍是否给出了至少一个备选并说明选择理由

### `convention-compliance` 规范一致性（10）
- 10分: 完全符合项目规范
- 8分: 基本符合，有合理且已说明的例外
- 5分: 部分偏离规范
- <5分: 严重偏离规范，或在无项目画像时自造了一套规范

必须逐项检查（项目画像为唯一评判基准；画像为空则按同目录既有代码写法推断）：
1. 组件写法、命名、目录归属、路由注册方式是否符合项目约定
2. 样式方案（语义 token / 变量 / 断点）、i18n（key 命名空间、语言包同步）是否按项目约定
3. 请求层、store 写法是否沿用项目既定模式
4. 是否有「合理的创新」——偏离规范的地方是否写了理由

## lane=be 六个维度（合计 100）

### `requirement-coverage` 需求覆盖（20）
- 20分: 完整覆盖所有需求点、验收标准与契约接口
- 16分: 覆盖主要需求，有小遗漏
- 12分: 覆盖部分核心需求
- 8分: 遗漏重要需求或遗漏契约接口
- <8分: 严重遗漏

必须逐项检查：
1. 契约文档里标为 `new` / `change` 的每个接口，方案是否都有对应的 Controller / Service / 数据落点
2. 每条验收标准能否在方案里找到落点（哪个接口 / 哪条业务规则负责它）
3. 需求梳理的异常流（并发、重复提交、权限不足、数据不存在）是否都有设计
4. 需求梳理的存量消费方排查结论是否被方案尊重（`change` 接口的兼容处理）
5. 范围边界（不做什么）是否被尊重，有没有越界设计

### `layering-contract` 分层与契约落地（20）
- 20分: 分层与入站类型完全符合项目约定，契约逐字段落地，模块边界无越界
- 16分: 分层合理，个别契约字段映射不清
- 12分: 存在跨层调用、入站类型混放或契约字段偏离
- <12分: 分层混乱或违反模块依赖禁令

必须逐项检查：
1. Controller / Service / Manager / Mapper 的职责划分是否符合项目分层约定；事务是否在 Service 层收口
2. 接口放在正确的入站类型包里，身份来源是否按入站类型取
3. 契约 `id` → Controller 方法 → DTO → VO → 错误码 的映射表是否完整；字段名、类型、可空性与契约一致
4. 对外契约是否只暴露项目规定的业务主键，没有泄漏数据库物理主键
5. 跨模块协作是否只走项目允许的机制，有没有互相注入 Service 或 Maven 依赖越界
6. 新接口是否需要网关 route，方案有没有写

### `data-model-index` 数据模型与索引（20）
- 20分: DDL 要点完整，通用字段、业务主键、索引、注释全部符合项目约定，迁移方案可回滚
- 16分: 表设计合理，个别索引依据或注释缺失
- 12分: 缺通用字段或索引设计无依据
- <12分: 违反项目数据库硬约束（如缺隔离键、暴露物理主键、缺逻辑删除）

必须逐项检查：
1. 新表 / 新字段是否遵守项目的命名前缀、字段类型、可空性、默认值、注释约定
2. 项目要求的通用字段（租户、空间等隔离键、逻辑删除、审计人与时间、版本、排序）是否齐全
3. 业务主键与唯一索引：每张核心表是否有对外业务主键且建了唯一索引；稳定业务标识是否建索引
4. 索引设计是否有依据（等值 / 范围 / 排序列顺序与查询条件对得上），有没有重复或无用索引
5. 数据量级预估与归档策略是否写了；历史表变更的迁移脚本与线上旧数据兼容是否有方案
6. 身份类字段的类型与存储口径是否按项目约定

### `transaction-concurrency` 事务·并发·幂等（20）
- 20分: 事务边界明确且不含外部调用，写接口幂等闭环，并发竞争点逐一封堵，事件一致性有方案
- 16分: 主要路径闭环，个别竞争点未分析
- 12分: 存在事务内外部调用，或核心写接口缺幂等设计
- <12分: 并发与一致性基本没考虑

必须逐项检查：
1. 多表写是否在事务内且回滚异常类型正确；大事务是否拆解
2. 事务内是否混入 HTTP / RPC / 消息发送 / 大文件处理——有则必须改为事件 / outbox，方案是否这么写了
3. 每个写接口的幂等键来源与重复提交的预期行为是否明确，与契约一致
4. 乐观锁 / 悲观锁 / 分布式锁的选型与粒度是否有理由；锁释放与超时是否考虑
5. 并发竞争点逐一列举了吗（同一资源并发写、先发后至、定时任务与用户操作冲突）
6. 涉及通知、统计、审计、外部同步的，是否先写 outbox / 事件表而不是直接调用

### `performance-security` 性能与安全（10）
- 10分: 慢查询风险点与越权校验落点全部识别并有方案
- 8分: 主要风险识别，个别缓存或限流点未写
- 5分: 存在明显 N+1 / 深分页 / 大 IN 风险未处理，或越权校验落点不明
- <5分: 信任了前端透传的身份 / 租户 / 金额，或存在注入风险

必须逐项检查：
1. N+1、深分页、大 IN、全量加载：方案是否逐个规避
2. 批量操作上限、分页深度上限是否按项目约定
3. 缓存 Key 是否带隔离维度、是否有过期、穿透 / 击穿 / 雪崩防护落点
4. 水平越权：资源归属校验在哪一层做，是否覆盖所有写接口与按 ID 读接口
5. 是否把前端透传的身份、租户、金额字段当可信输入；身份是否只从登录上下文取
6. 限流 / 熔断 / 降级点、外部调用超时与重试上限是否有

### `convention-compliance` 规范一致性（10）
- 10分: 完全符合项目规范（分层、命名、统一响应体、错误码、日志、事件、定时任务约束）
- 8分: 基本符合，有合理且已说明的例外
- 5分: 部分偏离规范
- <5分: 严重偏离，或在无画像时自造了一套规范

必须逐项检查（项目画像与 CLAUDE.md / crs 为唯一评判基准）：
1. 包结构与类命名是否符合项目约定；DTO / VO 写法与放置包是否按约定
2. 接口路径命名风格、统一响应体、全局异常处理是否沿用项目方式
3. 错误码是否引用项目既有体系，新增错误码是否说明理由
4. 定时任务、异步任务、线程池是否按项目约束归位
5. 禁止事项清单（项目明令禁止的库、字段名、物理删除等）是否无一触犯
6. 格式化 / 静态检查工具（如 spotless）是否在方案的完成判定里

## 汇总与判定

- `finalScore = round(Σscore / Σmax × 100)`；`passed = finalScore ≥ 80`；`maxRounds = 3`
- 不过线 → 把 `issues` 原文作为 `reviewIssues` 带回 ③ 方案（同泳道），`round+1`
