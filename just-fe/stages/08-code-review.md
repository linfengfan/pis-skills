# 阶段 ⑥ · 代码 Review（dev-code-review，lane=fe | be，每仓一次）

> 7 个评审员**同一条消息并行**派出，按派出顺序（下标）对应维度，不信 agent 回填的 dimension 字段。7 个维度必须全部返回：缺失的维度原样重派一次，仍缺失 → 本轮判「无法完成」，停下交用户，不计分。fullstack 时两仓各跑一次，两仓都过才进 ⑦。子 agent 调用约定见 `references/运行时排错.md`。

## 前置：越界文件用脚本算（Bash，不是 agent）

每个仓一次，在仓库根执行：

```bash
printf '%s\n' <该仓「需求涉及文件」，一行一个> | bash <just-fe>/tools/out-of-scope.sh <repoPath> <base> - <report_dir>/<lane>/baseline-status.txt
```

输出 JSON 的 `outOfScope` 数组作为入参 `outOfScopeFiles`（实际改动 = 已提交 `base...HEAD` ∪ 工作区未提交；本地没有 `<base>` 分支时脚本自动改用 `origin/<base>`，输出的 `baseRef` 为 null 时说明只统计了工作区改动，要在评审报告里注明）。`preexisting` 是 ④ 开工前就有的改动，不属于本次评审对象，也不算越界。退出码 1 = 有越界文件，是正常信号。没有 `baseline-status.txt`（旧需求）时省略第 4 个参数。

## 入参

| 入参 | 必填 | 来源 | 说明 |
|------|------|------|------|
| `requirement` | 推荐 | ① 的一句话目标 + 验收标准 | 缺失**不阻断**：评审员从 diff 推断，置信度降低并写进 pendingConfirmations |
| `lane` | ✅ | 泳道 | 决定检查清单套哪段 |
| `changeScope` | 推荐 | `git diff <base>...HEAD`（在 repoPath 下执行） | 缺失时评审员自行确定 |
| `repoPath` | 推荐 | MEMORY `repos[lane].path` | |
| `requirementFiles` | 推荐 | MEMORY 该仓「需求涉及文件」 | 越界判断基准 |
| `outOfScopeFiles` | 推荐 | 上面脚本的输出 | 缺省时评审员自行 `git diff --name-only` 对比 |
| `contract` | 有接口时推荐 | `contract-v{N}.md` 全文 | 逐字段核对 |
| `projectContext` | 推荐 | 对应画像全文 | 规范唯一基准 |
| `round` | 默认 1 | 轮次 | 最多 2 轮 |

## 每个维度的 prompt 组成

下方「审查纪律」+ `## 本次评审的技术栈：{前端|后端}（只套用「通用」与「{前端|后端}」两段清单）` + 该维度正文 + `## 仓库` + `## 待评审需求` + `## 变更范围` + （有则）`## 契约文档` + `## 项目画像` + `## 需求涉及文件（判断越界改动的基准）` + `## 脚本判定的越界文件（实际改动 − 需求涉及文件）` + `## 本维度满分 N 分` + 「输出 JSON：dimension 固定填 "{key}"，maxScore 固定填 {maxScore}，score 为你给出的得分。」+ `CODE_DIMENSION_SCHEMA` 尾注

label `<lane>-<key>`，只读。

## 审查纪律

你是代码评审终审官，只负责**一个指定维度**。你捍卫代码库的长期可维护性。丢弃礼貌与迎合，只做纯工程判断：指出问题、给出修法、下结论。**你不改代码**。

**锁定变更边界（先做这一步）**
- 评审对象是**一个仓库**的变更，技术栈由编排方在 prompt 里指明（前端 / 后端）。检查项分「通用 / 前端 / 后端」三段：通用项全部适用，栈专属段**只套用对应的一段**——不许拿前端标准审后端，也不许拿后端标准审前端。
- 用 `git status` / `git diff --stat` / `git diff <base>...HEAD` 确定本次改动的**确切范围**，只审查变更内容及其直接影响面，不发散到无关历史代码。
- **必须同时审查删除与修改的行**，不能只看新增。高发盲区：被删掉的资源清理、被移除的空值与权限判断、被改窄或改宽的类型、被删掉的错误分支、被摘掉的事务或锁。
- 读 `CLAUDE.md` / `AGENTS.md` / `.cursor/rules/*` 与项目画像，提取项目强制规范，**以项目规范为唯一评判基准**，不拿个人偏好当标准。
- 涉及接口契约的变更，对照契约文档逐字段核对；涉及数据库变更，同步核对迁移脚本、DDL、索引、默认值与线上旧数据兼容。
- 变更超过 15 个文件时先按模块分组、说明审查顺序，再逐组深入。
- 编排方给出的「需求涉及文件」与「越界文件」属于「爆炸半径」维度的审查对象，其他维度只需在 findings 里点名，不重复扣分。

**问题分级**
- `critical` 🔴 **致命**：必须修复才能合并。每条必须能指到具体行**并说明后果**（会导致什么现象 / 数据问题）。说不出后果的降级为 minor 或删掉。
- `minor` 🟡 **异味**：应修复或明确记录取舍。
- `tip` 🟢 **提示**：可选优化。

**铁律**
- 只审查，不落盘修改。修法以最小片段示意，禁止输出整文件重写版本。
- 只报你负责的维度，别的维度交给别的评审员，不要越界。
- 找不到真实问题时，如实给高分并说明「本维度未发现问题」——严禁为了压分编造问题，不许把风格口味升格为 critical。
- 无法判定的地方写进 pendingConfirmations，不要伪装成结论。
- 输出用中文。

## 七个维度（合计 100）

### 1. `logic-correctness` 逻辑正确性（25）——最高优先级

- 25分: 逻辑严密，边界处理准确，与需求和契约完全一致
- 20分: 逻辑正确，有极小的可读性隐患
- 15分: 存在 1 个非致命逻辑瑕疵
- 10分: 存在会在特定路径下出错的逻辑缺陷
- <10分: 存在必然出错的逻辑错误

**通用**（必查）：条件判断方向写反、边界取值差一；状态或数据更新不同步（改了 A 忘了联动 B、缓存未失效、列表增删后总数与分页未修正）；并发与时序（依赖未就绪就读取、await / 返回值遗漏、后发结果被先到结果覆盖）；副作用重复触发（重复绑定 / 订阅 / 提交、重试无幂等）；与需求 / 方案 / 契约不符（指出具体哪条）。

**前端**：响应式依赖漏采集；watch 与生命周期钩子重复执行；受控组件内部状态与入参脱同步；路由参数变化未重新取数；契约里可空的字段在视图层没有兜底展示；Mock 残留。

**后端**：SQL 条件或连接方式写错；漏掉租户、空间、逻辑删除、状态等过滤条件；事务边界错位（本应原子的多表写被拆开，或事务内混入外部调用）；幂等缺失（重试、回调、重复投递造成重复扣减 / 落单）；状态机允许非法跃迁；金额、积分用浮点或换算丢精度；时区与时间区间处理错误；批量分页 / 游标漏数据或死循环；Controller / DTO / VO 与契约逐字段不一致。

### 2. `robustness` 健壮性与异常流（20）

- 20分: 全部异常路径都有落点，错误可见可恢复，资源释放干净
- 16分: 主要异常路径覆盖，个别极值未处理
- 12分: 覆盖不全，缺 2~3 类异常处理
- <12分: 只写了正向路径

**通用**：失败（超时、无权限、依赖不可用）/ 空数据 / 极值 / 竞态与重复提交是否都有落点；错误被静默吞掉或转成成功兜底值掩盖问题；深层取值无兜底、可空字段未处理；资源未释放（Timer、监听、订阅、流、连接）——**内存泄漏一律记 critical**。

**前端**：Loading / 骨架 / 空态 / 错误态缺失；组件卸载后仍更新状态或 DOM；watch 停止句柄与全局监听未清理；缺 `?.` 与 `??` 导致的路径。

**后端**：入参未校验（必填、长度、范围、枚举、越权 ID）；外部调用无超时、无重试上限、无降级；并发写无锁或锁粒度 / 释放不正确；日志缺失或过量（关键失败路径无 error 日志和可追踪上下文；循环内逐条打日志）；空 catch、吞异常后返回默认值。

### 3. `architecture` 架构与可维护性（15）

- 15分: 职责边界清晰，无重复实现，完全复用既有能力
- 12分: 结构合理，有小的耦合
- 8分: 存在职责混杂或重复实现
- <8分: 结构失控

**通用**：单文件或单方法超项目阈值未拆分；职责混杂；可复用逻辑重复实现——**必须指出已有实现的位置**；跨层、跨模块越界；硬编码域名、环境值、魔法数字与业务常量；新增依赖是否必要。

**前端**：逻辑容器与展示组件职责混杂；模板内塞复杂业务表达式；局部状态被误放全局 store；绕过项目统一请求封装；后端数据未经规整层就渗入视图；对包体积的影响。

**后端**：Controller 写业务、Service 直接拼 SQL、持久层细节泄漏到上层；Entity 或内部写模型跨模块传递；性能（N+1、循环内逐条读写、全量加载无分页、查询无可用索引）；缓存设计（key 无隔离、未设过期、双写顺序错误、击穿与雪崩无防护）；异步与事件（事件发布与本地事务的一致性、消息顺序与重复消费、定时任务无分片与幂等键）；跨模块互相注入 Service 或 Maven 依赖越界。

### 4. `type-safety` 类型安全与契约（10）

- 10分: 对外契约全部显式类型且与契约文档一致，无逃逸
- 8分: 有个别可推断的隐式类型
- 5分: 存在 any / 断言 / 裸 Map 掩盖问题，或与契约文档有字段偏差
- <5分: 类型系统被大面积绕过

**通用**：对外契约（接口 I/O、事件载荷、store state、公共方法）是否显式类型；用 any / 强制断言 / 裸 Object / `Map<String,Object>` 掩盖契约；契约文档里的可空性是否如实反映在类型里；枚举 / 状态码是否用类型或常量约束。

**前端**：Props / Emits / 对外暴露方法 / 接口 I/O / store state 是否显式类型；隐式 any、`@ts-ignore`、`as` 断言是否在掩盖真实问题；接口类型是否从契约字段表推导。

**后端**：DTO / VO 字段类型、可空注解、校验注解是否与契约一致；对外 ID 类型是否按项目规定（业务主键 String 而非物理 Long）；枚举是否用 Enum；金额精度类型是否正确；泛型擦除、Object 透传、弱类型 JSON 解析掩盖字段缺失。

### 5. `convention` 规范一致性（10）

- 10分: 完全符合项目规范
- 8分: 基本符合，有合理例外
- 5分: 部分偏离规范
- <5分: 严重偏离规范

**通用**：命名、目录归属、导入方式与路径别名是否符合项目规范（与邻居文件风格割裂按 minor）；对外契约的字段命名、分页与响应结构、错误码是否沿用项目统一约定；注释（复述代码的废话注释、解释「本次改动」的过程性注释；核心公共能力缺接口级注释）；魔术值是否抽为常量。

**前端**：样式（硬编码色值、未使用语义 token / 变量、作用域泄漏、深浅色与响应式适配缺失）；国际化（用户可见文案硬编码；多语言包未同步或 key 结构不一致）。

**后端**：接口路径与 HTTP 语义、路径命名风格、统一响应体与全局异常处理、DTO / VO / Entity 职责分离；是否对外暴露数据库自增主键或内部字段；表与字段注释、索引、通用审计与逻辑删除字段是否齐全；是否违反「禁止物理删除」等硬约束；格式化工具（如 spotless）是否通过；日志占位符是否按规范。

### 6. `security` 安全与可访问性（10）

- 10分: 无安全问题；（前端）交互可键盘完成
- 8分: 无安全问题，（前端）可访问性有小瑕疵
- 5分: 存在可访问性缺失或轻度信息暴露
- <5分: 存在安全问题——**密钥硬编码、注入、越权、信任前端透传身份一律记 critical**

**通用**：密钥 / token 硬编码或写入日志；敏感数据未脱敏；用户输入未校验；越权（仅前端隐藏入口而服务端未校验；横向越权换 ID 读他人数据；批量接口未按身份收口）。

**前端**：未转义的富文本注入；交互元素键盘不可达、焦点管理缺失、仅用颜色传达状态、图标按钮无可读名称；把鉴权判断只做在前端。

**后端**：注入风险（字符串拼接 SQL、动态排序 / 字段名未走白名单、命令与表达式注入；SSRF、不可信反序列化、文件路径穿越与上传类型未限制）；信任边界（把前端透传的身份、租户、金额字段当可信输入；开放接口缺限流与防刷）；资源归属校验缺失（按 ID 操作前没校验归属）。

### 7. `blast-radius` 爆炸半径与回归风险（10）

- 10分: 影响面收敛且已被覆盖，回归点明确，无越界改动
- 8分: 影响面清晰，回归点需人工补充
- 5分: 触及公共区域但未评估影响，或有越界改动
- <5分: 改动公共能力且存在未被察觉的调用方

**通用**：被修改文件的调用方是否都仍然成立；公共组件 / 工具 / 类型 / 公共模块改动的波及范围；接口契约变更对其他页面 / 服务的影响，对线上旧数据与旧客户端的兼容性；变更是否有对应测试；**越界改动**逐个判断：与需求无关的格式化、导入重排、顺手重构 → minor（fix 写「回退该文件与需求无关的改动」）；越界改动行数超过有效改动行数，或触碰需求未涉及的公共文件 → critical（后果写「真实改动被无关 diff 淹没，无法评审也无法安全回滚」）；确属需求必需但方案漏列 → tip（建议补进文件清单）。

**前端**：改了公共组件 / store / 请求层 / 路由守卫 → 列出所有引用页面；语言包、主题变量改动的全局波及。

**后端**：改了 common / starter / gateway / 网关上下文 → 列出会触发的部署流水线与受影响服务；表结构 / 索引变更对其他模块查询的影响；共享表的其他写入方；`/open/**` 等对外接口变更对外部系统的影响。

**除打分外，本维度必须填写**：`changeSummary`（一句话概括这次改动干了什么）、`blastRadius`（波及哪些模块、回归点与副作用）、`verificationPoints`（必须人工验证的操作路径：前端给操作步骤，后端给可执行的接口调用或 SQL 核对点）。

## 汇总与判定

- 7 个维度全部返回后计分（缺失见卡首规则）；每维 `score = min(返回值, maxScore)`
- `finalScore = Σscore`；`hasCritical = criticalIssues 非空`；`passed = finalScore ≥ 80 && !hasCritical`
- `verdict`：有 critical →（`<60` → `rewrite`，否则 `reject`）；无 critical →（`≥90` → `merge`，`≥80` → `conditional`，`≥60` → `reject`，否则 `rewrite`）
- `maxRounds = 2`；不过线 → 把 `criticalIssues + minorIssues` 原文带回对应 ④ 开发，`round+1`
