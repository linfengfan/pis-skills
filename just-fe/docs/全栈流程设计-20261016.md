## 一、已定决策

| 决策 | 结论 | 直接后果 |
|------|------|----------|
| 仓库形态 | **前后端各一个 git 仓库 + 一个会话区**，三者并列在同一个 `.code-workspace` 里 | 流程产物落会话区；`changeScope`、越界检测、⑥ 评审、⑧ 提交清单按仓各算一次 |
| 提交权 | **流程不执行任何 git 写操作**（`add` / `commit` / `merge` / `push` 全部由用户做） | ⑧ 只产出变更说明 + 每仓的待提交文件清单 + 建议 commit message；部署闸门只产出命令 |
| 契约归属 | **契约先行** | ② 拆出独立契约阶段；FE 的 Mock 与 BE 的 DTO 都从契约生成；契约改动升版本重评 |
| 后端运行时 | **不能本地跑，依赖远端 dev 环境** | ⑤ 等的是「部署」不是「接口」；BE 本地只跑单测与 `@WebMvcTest`；需要 DB 的集成项与打真后端的 E2E 要么对 dev 环境跑，要么标 `unverified` |

默认假设（按真实仓库修订，未另行指定即按此执行）：

- 后端栈按 `server-platform/CLAUDE.md`：Java 21 / Spring Boot 4.0.5 / Maven 多模块 / MyBatis-Flex / MySQL 8 / Redis + Redisson / Sa-Token；`Result` 统一响应体（成功码 200）、`ErrorCode` + `BusinessException`、DTO/VO 用 record、对外只传 `{entity}Id` String 业务主键、接口路径小驼峰
- 后端**尚未接 OpenAPI**（CLAUDE.md 明示「后续统一接」），契约不写 YAML 进后端仓，用 Markdown + 机器可读 JSON 块放会话区
- 部署为 Gitee Go（`.workflow/*.yml`）：后端 push 到 `dev` 分支、前端 push 到 `develop` 分支自动触发；后端按模块 + 路径过滤各一条流水线
- 两仓使用同名特性分支，记入 MEMORY

## 三、形态：一条流水线、两条实现泳道、契约做同步点

```
⓪ 工作区确认（report_dir / repos[] / scope / source / dev 网关）
        │
① 需求梳理（栈无关；产出 stackScope；接口需求逐条三态：已有(证据位置) / 需新增 / 需变更）
        │  任一「需新增 / 需变更」→ repos[be].mode 必须是 write，否则停下问用户
        │
② 契约设计 ──▶ ⛩ ──▶ ③a 契约评审（3 维并行，<80 打回②，最多 2 轮）
        │  先 grep 后端仓 controller/openapi 勘察，再定义；产出 contract-v1.md（含 JSON 块）
        ├────────────────────┬────────────────────┐
   ②-FE 前端方案          ②-BE 后端方案（be.mode=write 时）
        │                      │
   ③-FE 方案评审 6 维      ③-BE 方案评审 6 维
        └────────────────────┴────────────────────┘
                             ⛩  一道闸（两泳道都过才开）；scope=② 在此停
        ├────────────────────┬────────────────────┐
   🎨 设计稿闸门            （无）
   ④-FE UI 开发            ④-BE 接口开发
   Mock 按契约 JSON 生成     @WebMvcTest 契约测试 + mvn -pl <module> -am test 本地过
        └────────────────────┴────────────────────┘
                             ⛩  🚀 部署闸门：把 server 特性分支合入 dev 并 push → 等 Gitee Go → 用户回复「已部署」
                             │
⑤ 联调 = 脚本对 dev 网关跑契约符合性校验 ──▶ FE 换真接口（去 Mock）
                             │
⑥ 代码 Review：每仓一次（7 维 × 2），每维 prompt 带「通用 / 前端 / 后端」清单；越界检测脚本做
                             │  两仓都 ≥80 且无 🔴
⑦ 测试评估：BE 单测+契约测试（本地）；FE E2E 打 dev 网关；需 DB 的集成项 unverified
                             │  任一验收 / 回归 / 契约测试失败一票否决
⑧ 变更说明 + 提交清单：每仓一份「待 add 文件 + 建议 message（带 contract-v{N}）」，建议顺序先 server 后 web；
   流程到此结束，是否 commit、何时 commit、是否合入 dev / develop 全部由用户决定
```

`stackScope=fe` 且 `be.mode=readonly`：契约阶段退化为「勘察 + 复用清单」（仍要做，是 FE 方案的依据），BE 泳道、部署闸门不启动。

**与上一版纪要的修正**：此前判断「后端进来后 ⑤ 的外部等待消失」不成立。等待从「等后端人」变成「等部署动作」，是流程里唯一必须由人完成的物理步骤（合入共享分支 `dev`），用部署闸门显式承认。

## 五、产物与状态

### 5.1 契约文档 `contract-v{N}.md`

后端没有 OpenAPI，契约是 Markdown。结构借用需求处理范式阶段二（见第九节），因为它的读者正是「只关心自己那块的协作方」：

```
# 契约 v{N} · {需求}
## 1. 范围与不覆盖（DV-1）
## 2. 变更本质：什么变了 / 什么没变（DV-2）
## 3. 责任矩阵（DV-3）：接口 × 前端 / 后端模块 × 状态（已有复用 / 新增 / 变更 / 不需要）
## 4. 复用清单（DV-4）：已有接口逐条 + 证据位置（文件:类:方法）+「不要再造」禁令
## 5. 关键标识来源辨析（DV-7）：spaceId / teamId / projectId / userId 哪个场景取哪个
## 6. 接口定义（每个接口一节）
   路径 / 方法 / 模块 / 入站类型（controller | openapi | op | adminapi）/ gateway route 是否需新增
   请求 record 字段表（名 / 类型 / 可空 / 校验 / 说明）
   响应 record 字段表
   错误码（引用 ErrorCode）
   ```json contract
   { "id": "...", "path": "/api/platform/...", "method": "GET", "module": "platform-points",
     "request": {...}, "response": {...}, "errors": [...], "status": "new" }
   ```
## 7. 存量消费方排查（IM-2，仅「变更」类接口）
## 8. 双向契约与废弃项（DV-8）
## 9. 可勾选验收（DV-11）
```

`json contract` 块是 `tools/contract-conformance.js` 与 ④-FE Mock 生成的输入。

## 六、分仓带来的具体规则

| 事项 | 做法 |
|---|---|
| `changeScope` | 各自 `path` 下 `git diff <base>...HEAD`，分别传给 ⑥⑦ |
| 越界检测 | 脚本：`git diff --name-only <base>...HEAD` 减去 `requirementFiles[lane]`；结果作为 ⑥ 爆炸半径维度的事实输入 |
| ⑥ 评审 | 同一脚本按 `lane` 跑两次；两仓都 ≥80 且无 critical；打回只回对应泳道 |
| ⑧ 提交清单 | 流程**不执行** `git add` / `commit`。产出每仓一份：`completedFiles` 作为待 add 清单、越界文件单列提醒回退、建议 message（后缀 `[contract-v{N}]`）、建议顺序先 server 后 web。用户自己决定提交与合入 `dev` / `develop` |
| 后端模块定位 | 契约阶段按 CLAUDE.md 模块职责表 + grep 定 `be_modules`；④-BE 的 `mvn -pl` 与部署闸门都只盯这些模块 |

## 七、后端不能本地跑带来的具体规则

| 阶段 | 本地能做 | 只能对 dev 环境 / 标 unverified |
|---|---|---|
| ④-BE | `mvn -pl <module> -am compile`、`mvn spotless:check`、`mvn -pl <module> -am test`（已有 345 个测试文件，`@WebMvcTest` 不依赖 DB） | — |
| 部署闸门 | 流程产出命令：`git checkout dev && git merge --no-ff feature/x && git push`；**由用户执行** | Gitee Go 自动构建部署；用户回复「已部署」后继续 |
| ⑤ 契约校验 | `tools/contract-conformance.js`：读 `json contract` 块 → 对 `env.dev.gatewayUrl` 逐接口请求 → 比对 `Result.code`、必填字段、类型、错误码 | 鉴权由 `env.dev.auth` 提供；拿不到凭证的接口 `unverified` |
| ⑦-BE | 单测 + 契约测试回归 | 需要 MySQL / Redis 的集成测试 → `unverified`，进人工验证清单 |
| ⑦-FE | — | E2E 打 dev 网关；不可达 → `unverified`。注意 fe-profile 记录「无业务 e2e 框架」，首次需补最小 Playwright 用例 |

一票否决：验收 E2E 失败、既有测试回归失败、**契约测试失败**、**契约符合性校验有 FAIL**。

`be-profile.md` 必填：技术栈版本、`build` / `test` / `lint(spotless)` 命令、模块 → 流水线 → dev 域名表、分层约定与入站四类（controller / openapi / op / adminapi）、`Result` / `ErrorCode` / `BaseEntity` 位置、数据库约定摘要（`mp_` 前缀、通用字段、业务主键）、`crs/` 与 `doc/` 索引、高风险模块（gateway、common、两个 starter——改它们会触发多条流水线）。

## 九、需求处理范式与 triage 的关系

`sessions/web-app/需求处理范式.md` 定义了阶段一（需求榨取：IN-1…5 / MD-1…7 / IM-1…4 / DC-1…3）与阶段二（协作降维：DV-1…12），并规定三条动作不可裁剪：`MD-3` 覆盖缺口反推、`IM-2` 存量消费方排查、`DV-7` 关键标识来源辨析。

对照 just-fe 现状：

| 范式要求 | just-fe ① 现状 | 差距 |
|---|---|---|
| IN-1 逐条编号台账，原文与解读分列 | `userStories[]` / `acceptanceCriteria[]` 散列 | 无 REQ-n 编号，无明确度评级 |
| IN-3 术语表先于建模 | 无 | 口径类需求（积分：总量 / 可用 / 冻结）必返工 |
| IN-4 现状勘察带证据 | `impactScope[]` 字符串 | 不要求证据位置 |
