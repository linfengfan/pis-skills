# just-fe 混合编排研讨纪要

**日期**：2026-09-22
**参与方**：用户、Claude（just-fe 维护者视角）
**主题**：混合编排模式（Workflow + Agent）在 just-fe 中的应用与改进方向

---

## 一、背景与共识

用户提出了一个行业观点：

> 在 Claude Code 动态工作流中，宏观上用 Workflow（确定性编排），微观上用 Agent（自主执行）。二者结合使用。

**共识确认**：just-fe 当前已经在实践这个理念，但实现方式与 ai-berkshire 不同。

---

## 二、现状分析：just-fe 的混合编排架构

### 2.1 宏观编排层（主 Agent / SKILL.md）

- **阶段串联**：①需求梳理 → ②方案架构 → ③方案评审 → ④UI开发 → ⑤接口联调 → ⑥代码Review → ⑦测试评估 → ⑧变更说明
- **控制机制**：阶段闸门、打回规则（80分红线）、MEMORY.md 状态管理
- **编排者**：主 Agent（你），负责路由、协调、汇总

### 2.2 微观执行层（Workflow 脚本内部）

- `architecture-review-workflow.js`：6 维度并行评审
- `code-arch-review-workflow.js`：7 维度并行审查
- `api-integration-workflow.js`：3 步骤串行（清单 → 联调 → E2E）

### 2.3 模式 A vs 模式 B 的选择

| 判断依据 | 工具列表里有没有 `Workflow` |
|---------|--------------------------|
| **模式 B** | 有 → `Workflow(scriptPath)` 直接跑脚本 |
| **模式 A** | 没有 → `Agent` 工具手工编排（主 Agent 还原脚本逻辑） |

模式 A 是**降级路径**，主 Agent 需承担：读脚本 → 取 prompt/schema → 派子 agent → 汇总 → 写报告

## 三、对比分析：just-fe vs ai-berkshire

### 3.1 调用链路对比

| 维度 | just-fe | ai-berkshire |
|------|---------|--------------|
| **宏观编排** | SKILL.md + 主 Agent | Team 工具 + team-lead |
| **并行粒度** | 评审维度（6-7 个并行） | 分析师角色（4 个并行） |
| **通信机制** | 脚本返回值（同步拉取） | SendMessage（异步推送） |
| **进度感知** | 等待返回后才知道完成 | 实时接收消息更新进度 |
| **资源清理** | 无显式清理 | SendMessage(shutdown_request) |

### 3.2 关键差异：推送 vs 拉取

**just-fe（拉取模式）**：
```
Workflow(scriptPath) → 等待返回 → 读 passed/score/issues
```
主 Agent 在 Workflow 运行期间是"盲等"。

**ai-berkshire（推送模式）**：
```
Task(parallel) × 4 → 各角色独立执行
     ↓ SendMessage(type: "message")
team-lead 实时接收，边收边处理
```
team-lead 可以边收边更新进度，不用等全部完成。

### 3.3 相同点

| 维度 | just-fe | ai-berkshire |
|------|---------|--------------|
| 混合编排理念 | ✅ Workflow（宏观）+ agent()（微观） | ✅ Team（宏观）+ 子 Agent（微观） |
| 并行隔离 | ✅ 维度/角色独立，不共享 context | ✅ 同上 |
| 汇总判决 | ✅ 主 Agent 汇总 + 打分 | ✅ team-lead 汇总 + 准出判决 |
| 工具补强 | ✅ Bash 跑 E2E/金融计算 | ✅ Bash 跑 financial_rigor.py |

## 四、待讨论：引入 SendMessage 的影响

### 4.1 潜在收益

| 收益 | 说明 |
|------|------|
| **进度可视化** | 子 Agent 完成后主动推送，主 Agent 实时更新进度表 |
| **资源管理** | 引入 TeamDelete，显式清理团队资源 |
| **容错性** | 单个维度失败不影响其他维度独立完成 |
| **异步友好** | 适合耗时较长的任务，用户可边等边看进展 |

### 4.2 潜在问题（待讨论）

| 问题 | 影响 |
|------|------|
| **复杂度增加** | Team 工具的引入、team-lead 异步消息处理、shutdown 后的状态同步 |
| **模式一致性** | 引入 Team 后，模式 A 的手工编排是否仍适用？ |
| **上下文管理** | SendMessage 的内容如何控制大小，避免主上下文溢出？ |
| **状态一致性** | 并行执行时，MEMORY.md 的更新时序如何保证？ |
| **成本考量** | Team 模式下多个 Agent 并行，Token 消耗显著增加 |
