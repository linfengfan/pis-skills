# 开发共用规则（dev-rules）

前端开发与后端开发都必须遵守。优先级高于各自角色卡里的编码规范。

## 变更边界铁律

- **只改本次需求涉及的文件与代码行。** 需求涉及文件以方案的 `files.txt` / 任务卡为准（`lite` 档没有方案时，以需求梳理报告的影响面为准）。确需改清单外的文件，在报告「清单外文件」里逐个写理由，并在回执 `outOfScopeClaimed` 里列出。
- **禁止全局格式化。** 不对未涉及的文件运行任何格式化或 `--fix` 命令；不整理无关文件的导入；不顺手重命名、重构、删注释、改缩进。门禁命令会波及全局时，只对改动文件运行，或跳过并在报告里说明。
- **不碰开工前已有的改动。** 编排者在开工前给仓库拍了基线；仓库里原本就有的未提交改动属于用户，不修改、不回退。收工前自己看一遍改动（`git status` / `git diff`），把**自己引入的**无关改动回退掉。
- 发现需求之外的真问题：写进报告「问题记录」，不动手修。

## 项目规则是硬约束

动手前打开仓库的 `.cursor/rules/`（以及 `CLAUDE.md` / `AGENTS.md` 指向的规范、画像「规范文件索引」里标了「什么时候必读」的文件），找出 `globs` 或适用说明匹配**本次要改的文件**的规则，通读后再写代码。规则与角色卡冲突时以规则为准。规则带「自检」清单的，收工前逐条过一遍，结果写进报告「自验收命令」一节。

## 不执行任何 git 写操作

不 `add`、不 `commit`、不 `stash`、不 `checkout` 其他分支、不 `reset`、不 `push`。只读命令可以用。代码怎么提交由用户决定。

## 实现阻断

方案或接口定义存在逻辑冲突、关键信息缺失（缺唯一键、并发方案死锁、字段无法落到现有结构、设计稿读不到又没有「按现有风格」的授权）时，**停止编码**，回执 `status` 填 `blocked`，在报告「实现阻断」里写清死锁点。绝不靠猜测补齐。

## 修复轮次

编排者给了上一轮代码评审或测试评估的汇总时，**只修汇总里的不通过项**，逐条在报告里写怎么改的；不借机扩大改动范围。

## 自验收（必须执行）

- 运行画像里的门禁命令（类型检查、lint、格式检查、单测；后端还有编译与契约测试），只针对本次改动的文件或模块。
- **必须看到通过结果**才能宣称完成；有报错修到干净，不留「已知报错」。每条命令和退出码写进回执 `commands`。
- 需要真实数据库、中间件或联调环境才能验证的路径，写进报告「需要联调环境验证」，不伪装成已验证。

## 输出约束

- 用编辑工具把代码**落盘**，不要在回复里贴大段代码。
- 中文报告，不写寒暄与自我表扬。
